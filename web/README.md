# Quarrix Web 4.1.1

A React/Vite and Express portal, live at https://quarrix.nexonictechnologies.com. It uses the same header, footer, tokens and typography (Fraunces + Inter) as the nexonic WordPress theme on nexonictechnologies.com; the theme layer is the first section of `src/styles.css` and the shared header/footer markup is in `src/shell.jsx`. When the main theme's menu or footer changes, update `shell.jsx` to match. The existing Electron desktop package remains 3.9.0 and uses its own local database.

## Local run

Node 24 or newer. Inside `web/`, run `npm ci`, `npm test`, `npm run build`, and `npm start`. Open http://127.0.0.1:4322. Local mode uses SQLite under `data/`; the encryption key is created locally with restrictive permissions. Do not reuse the development database or key for production. For Vite development, run the backend with `PUBLIC_ORIGIN=http://127.0.0.1:5173` and start `npm run dev` in a second terminal.

## What is built

- Guest discovery: up to ten returned results and five searches per browser per UTC day. An account unlocks 50 searches/day with up to 50 results each. A cookie-based guest allowance is a convenience gate, not a resilient anti-abuse identity mechanism. Add verified reverse-proxy limits and a bot challenge before public registration.
- Live Jobicy remote jobs, Arbeitnow European vacancies, French government business registry and posted Grants.gov opportunities; actual source links, capped results, timestamps, shared in-memory cache, bounded concurrency and explicit partial/unavailable/stale status. Coverage is not worldwide business parity; provider permission checks precede every added source. Sources are self-reported, not verified as guaranteed legitimate.
- Account email/password, transactional-email verification and password reset when SMTP is configured, account deletion, records and PDF uploads. Login on a second device loads the same workspace. Google login and desktop synchronization are not implemented yet.
- Workspace for profiles, business records, customers, applications, saved opportunities, resume notes, and 30-day encrypted search history (last 50 shown). Documents are downloadable only by their owner or authorized support, PDF only, 2 MB/file and 10 MB/account, served as attachments. Production uploads and downloads require a clean local malware screening result; on Hostinger they remain temporarily unavailable. Existing documents remain encrypted, listed and deletable by their owner; resume notes are unaffected.
- Newsletter consent is optional and separate from account registration. Only verified, opted-in addresses are marked subscribed; users can unsubscribe. Campaign sending is not implemented.
- Optional server-side OpenRouter assistant: three prompts/account/day, thirty total/day, explicit consent per question, limits persisted, free model only. No documents or account data sent automatically; user must avoid personal information. No paid fallback. Core search needs no API key. Configure and verify an OpenRouter key and free model independently; provider availability and quotas are external.
- Owner dashboard plugin in `wordpress/quarrix-admin`: accounts, verification, subscription consent, search counts, record/document counts, suspend/restore, portal maintenance mode, audited support access. Suspended users lose sessions; restoring requires a new login. Support access requires explicit user permission, expires after one hour, and can be revoked. Owner may then view private records, recent searches and download documents; accesses are logged. Never use support access for marketing.

## Security boundaries

Abuse limits are ordered so that unverified traffic cannot use anyone else's allowance: sign-in, registration, recovery and guest search verify the Turnstile challenge first, and only then count against limits. In-memory limits are per client address or per account (never one site-wide counter). Persisted ceilings apply across restarts and workers: 25 registrations/day, 100 transactional emails/day, 3 recovery emails per address/day, 10 sign-in attempts per account per 15 minutes, and configurable shared ceilings (`GUEST_SEARCHES_PER_DAY`, default 250; `MEMBER_SEARCHES_PER_DAY`, default 2,000; `LOGIN_ATTEMPTS_PER_15_MIN`, default 1,000). Personal allowances are checked before shared ones, and a search that could not reach its source is refunded. Forwarded client addresses are only trusted when `TRUST_PROXY_HOPS` is set to the number of proxies in front of the app; otherwise the socket address is used. Database queries time out after 10 seconds, and per-account work is serialized per account rather than through one global queue. The versioned privacy notice is acknowledged at new registration; existing accounts are not retroactively marked as having acknowledged it. Newsletter consent remains independent and optional.

Passwords use salted scrypt hashes, session and email token digests are stored rather than raw tokens, production cookies are HTTPS-only and HttpOnly, browser writes require same origin. Email addresses, document names/contents, private records and search history are encrypted with AES-256-GCM and owner-bound associated data. Account IDs, timestamps, usage counts, record types, and document sizes are metadata, not encrypted. The server must be trusted: this is application-level encryption, not end-to-end encryption. Back up the key securely outside the database; losing it makes records unreadable. Admin audit records are append-only through the application, not tamper-proof against the database owner. Never expose the owner token or keys to browsers. Use strong WordPress 2FA, least privilege and restricted access to hPanel.

## Hostinger deployment

Deployed as a Hostinger Node.js app (Express, Node 24, root `web/`, entry `server/index.mjs`) with Git auto-deploy from `main`: every push to `main` rebuilds and restarts the live site, so merge only reviewed changes. The original setup was: create a distinct Node.js web app for `quarrix.nexonictechnologies.com` using existing Unlimited plan (2 CPU, 3 GB RAM, 50 GB disk shared with other sites). Do not overwrite WordPress or modify existing mail DNS records. Use Node 24, `web/` project root, `npm ci`, `npm run build`, entry file `server/index.mjs`. Use a dedicated MySQL DB/user and environment settings in hPanel:

| Variable | Purpose |
| --- | --- |
| `NODE_ENV=production` | Production defaults |
| `PUBLIC_ORIGIN=https://quarrix.nexonictechnologies.com` | Exact HTTPS origin |
| `DATABASE_URL` | Dedicated MySQL connection URL |
| `DATA_KEY` | Base64-encoded 32 random bytes, backed up securely |
| `ADMIN_TOKEN` | Independent, high-entropy access token (32+ characters) |
| `SMTP_URL`, `MAIL_FROM` | Transactional verification and recovery delivery |
| `ALLOW_REGISTRATION=false` | Keep closed until all production gates pass; enable later |
| `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET`, `TURNSTILE_HOSTNAMES` | Cloudflare Managed widget. Set all three together; production hostname must exactly match `quarrix.nexonictechnologies.com`. Public registration requires a complete configuration; signup, login, recovery and guest discovery require server-verified challenge tokens once configured. Never commit the secret. |
| `PRIVATE_REGISTRATION_EMAIL`, `PRIVATE_REGISTRATION_TOKEN_HASH`, `PRIVATE_REGISTRATION_EXPIRES_AT` | Optional private launch invitation: exact tester email, SHA-256 hex digest of a random 32-byte hex code, and ISO UTC expiry within 24 hours. Keep public registration off. The code is entered on the registration form and never stored as plaintext on the server. A successful claim is durable and single-use. Removed from the live app on 23 Nov 2026. SMTP and standard email verification remain mandatory. |
| `TRUST_PROXY_HOPS` | Optional. Set only if all ingress paths have a verified, consistent trusted proxy chain. Hostinger confirmed direct-origin headers cannot be trusted and its CDN is the current ingress. Leave unset on this deployment; the optional durable visitor-IP budget is inactive. |
| `PDF_SCANNER_PATH` | Absolute path to a local ClamAV-compatible `clamscan` executable with maintained signatures. Production PDF uploads and downloads fail closed without a configured and functioning scanner; existing documents are preserved in quarantine. |
| `GUEST_SEARCHES_PER_DAY`, `MEMBER_SEARCHES_PER_DAY`, `LOGIN_ATTEMPTS_PER_15_MIN` | Optional shared daily/15-minute ceilings (defaults 250, 2000, 1000). |
| `MAX_ACCOUNTS=500` | Initial registration cap, increase only after measuring shared hosting capacity |
| `OPENROUTER_API_KEY`, `OPENROUTER_MODEL` | Optional free model ending in `:free`; not set by default |

The WordPress plugin must be installed only after the portal is staged and verified. Put `QUARRIX_OWNER_ID`, `QUARRIX_API_ORIGIN` (exact HTTPS origin, no trailing slash), `QUARRIX_ADMIN_TOKEN` (same independent server secret) in server-side `wp-config.php`. Never put secrets in Git, plugin source, public paths or a chat. The owner ID is the exact WordPress administrator account, not every administrator role. Plugin actions require WordPress nonces, explicit owner access and server bearer authentication. Add a separate menu/product link on the existing site only after verifying the portal, WordPress controls and a private staging account.

## Verification and outstanding gates

Local automated suites cover account isolation, login on another device, encrypted records/PDFs, guest and registered access, newsletter preference, authorized support and revocation, suspension, maintenance, CSRF origin enforcement, account deletion, email verification and reset using a test delivery function. Live checks returned real data on Nov 23, 2026; no live OpenRouter or SMTP credentials used. Desktop typecheck and existing desktop tests passed. Built UI verified in browser; initial Jobicy live search returned three results, expanding to Jobicy and Arbeitnow returned thirteen results.

Before deployment: verify MySQL integration (Web CI includes a disposable MySQL service), PHP lint and real WordPress test install, actual SMTP delivery/verification/reset, secret rotation and backup restore, protection against guest cookie resets and distributed abuse, privacy and consent notices, provider terms and cache TTLs, load test shared host, confirm SSL and isolated application deployment, accessibility/mobile and production security review, malware scanning policy. Full desktop feature parity, more authorized data sources, Google login and desktop sync remain future work. Do not enable public registrations until production gates pass.

### 4.1.1 hardening release

The previous candidate passed SQLite and MySQL CI, web build, production dependency audit, WordPress PHP lint and desktop CI. Hostinger confirmed that automated website-file protection is active but no approved on-demand ClamAV executable is exposed. New PDF uploads and downloads fail closed; existing encrypted attachments are retained for future screening. Do not set a placeholder scanner path or send private documents to a third party. Hostinger confirmed direct-origin forwarded headers cannot be trusted; leave proxy hops unset until all ingress paths can be verified. Hourly external health monitoring has been configured. A scheduled database backup was confirmed (24 November 2026, 00:56 PKT); an isolated restore and decryption verification remain pending. Desktop installers remain at 3.9.0; desktop source changes require a subsequent installer release with its own platform gates.

Account recovery and session issuance use short database transactions and account row locks, and per-owner creation caps are evaluated in transactions. MySQL pool acquisition is bounded and connections with timed-out commands are destroyed; a connection loss during commit can still have an indeterminate outcome, so clients should verify state before retrying. Guest cookies are authenticated; an extra durable visitor budget requires verified proxy topology. `/api/ready` performs a database check; `/api/health` remains a lightweight liveness endpoint. Review sanitized runtime errors and validate alert delivery. The PDF scanner uses private temporary storage and does not transfer documents to a third party. Existing attachments are screened before delivery and remain unavailable when the scanner cannot run. Before production deployment, verify the current candidate's CI, review residual edge limits, and validate backup recovery in an isolated database; installer signing is a separate desktop release gate. Do not claim full production certification on local tests alone.
